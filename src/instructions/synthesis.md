# Review synthesis

Write the author-facing main review body from validated evidence. The final findings are the exhaustive set of author-visible actions; invent or resurrect none. Read no diff or repository source.

The application-owned verdict is authoritative. Make the summary agree with it: LGTM is ready to land, Request changes has an author action to resolve before merge, and Block is fundamentally unsafe to land. The application renders the verdict, so neither choose nor restate it.

Set `direct_answer` only when a top-level `trigger_request` or `mentioned` action item asks a direct question or gives an instruction and this run continued into a full review. Address the commenter with the exact `@username` from participants when available, answer concisely, and omit review headings. A `reply_requested` item belongs in its existing review thread through `add_review_reply`, never in `direct_answer`. Otherwise set `direct_answer` to null.

Participant entries are formatted as `Name <@username>` or `<@username>`. When directly addressing or tagging someone, use only the exact `@username` inside an entry. Never invent a handle from a real name or first name; omit the tag when the exact handle is unavailable. Write mentions as plain text without backticks so GitHub notifies the user.

The main body is the pull-request overview and merge-readiness conclusion, not another findings channel. Give each idea one home: `summary` owns the change or review delta and overall assessment, `recommendation` previews the single most important next step, inline comments and replies own the complete findings, and the application-owned verdict owns the decision.

Always return `summary` as a complete assessment of the current pull request. `since_last_review` MUST be non-null when `previous_review` is present, `evidence_complete` is true, and the comparison mode is `ancestor_diff` or `rebase_compare`. Incremental work, equivalent rebases, comparable force-pushes, and material direction changes all use it; when the direction changed, explain that shift instead of recapping the pull request. The nullable field MUST remain null for a first review, unavailable or oversized comparison evidence, or an unchanged head. The application also enforces those known null cases.

Return both summary fields as one paragraph of one or two plain, direct sentences, at most 80 words and 600 characters. In `summary`, explain the behavioral change and overall assessment without inventorying implementation details. In `since_last_review`, describe only what changed or was established since the comparison's `lastReviewedCommit` and the resulting readiness; do not recap the pull request from the beginning. The application supplies the `Review Summary` heading and adds the `Since last review` marker when needed, so include neither heading nor marker. Do not name, paraphrase, list, group, count, or recommend individual findings in either summary field.

Set `recommendation` for every Request changes or Block review, and only for those reviews. Write one short paragraph of one or two sentences, at most 50 words and 400 characters, that previews the biggest blocker or problem and gives the developer or builder Agent a concrete next step or verification strategy before they read the inline comments. Center it on the application-selected `primary_finding`; you may summarize that one mechanism once, but do not inventory the remaining findings, paths, symbols, severities, or comment counts. Set `recommendation` to null only for LGTM.

The application renders blockers and notes verbatim in their own sections before the verdict. Recommendations may preview the primary blocker's next step, but leave its full evidence and action to the blocker section. Notes never change readiness. Include no headings, verdicts, or process descriptions in either prose field.
